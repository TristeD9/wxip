# 开发日志

记录这个项目从零到可用过程中解决的问题。文中所有公网 IP、域名、服务器、
企业微信 corp_id / agentid / 应用编号 / 应用名称均为脱敏后的示例值。

## 一、项目搭建

需求：前后端分离，Python 后端；扫码登录企业微信；登录后自动把 iKuai 的公网 IP
覆盖写入所有企业微信自建应用的「企业可信 IP」；只保留最新一条。

技术选型：

- 后端 FastAPI + Playwright + SQLite，前端零构建原生 ES Module SPA；
- 镜像基于 `mcr.microsoft.com/playwright/python`，自带 Chromium。

关键结论：企业微信**没有**开放"修改自建应用可信 IP"的公开接口，只能复用管理后台
自身的请求。因此采用"手动录制一次真实请求 → 生成带占位符的模板 → 同步时逐应用重放"
的方案，而不是硬编码某个可能随时变更的内部接口。

## 二、企业微信扫码登录

最初按常规思路在主文档里找二维码元素，结果一直失败。抓取真实 DOM 后发现：

```
主文档   images=0 canvases=0
iframe  https://work.weixin.qq.com/wework_admin/wwqrlogin/mng/login_qrcode?...  images=1
```

二维码在一个 **跨域 iframe** 里，`page.locator()` 不会穿透 iframe。改为三级策略：
先用 `page.frame_locator("iframe[src*='login_qrcode']")` 取 iframe 内的图片，
再退到主文档候选元素，最后用容器元素整体截图兜底。

## 三、扫码登录态与标签页

出现过"同步能成功、自动发现却总失败"的怪现象。排查发现：

- 写可信 IP 走的是 `context.request`，依赖 Cookie，所以一直正常；
- 自动发现需要**导航页面**，而管理后台的登录态与完成扫码的那个标签页绑定，
  新开标签页会被重定向回登录页。

对策：新增 `select_authenticated_page()`，优先复用扫码成功那个标签页；找不到时才
新开，并负责关闭。同时把"登录态失效"和"抓不到列表"分成两种错误提示。

另外确认：**服务重启后企业微信登录态必然失效**（不落盘），需要重新扫码，这是企业
微信的机制。

## 四、iKuai 真实固件联调

第一版按社区常见写法用表单登录，设备返回：

```
{"ErrMsg":"Post data error","Result":10001}
```

不猜格式，直接探测。结论有三条：

1. **登录必须用 JSON 报文**（`Content-Type: application/json`），表单会被拒绝；
   登录改为"JSON 优先、表单回退"，兼容新旧固件。
2. **`sess_key` 通过 `Set-Cookie` 下发**，响应体只有 `{"Result":10000}`；
   改为先从响应体找、找不到再从 Cookie 取。
3. **WAN 查询函数名不是 `wan_status`**，而是 `wan`：

   ```
   POST /Action/call
   {"func_name": "wan", "action": "show", "param": {"TYPE": "total,data"}}
   → {"Result":30000,"Data":{"data":[{"pppoe_ip_addr":"203.0.113.10", ...}]}}
   ```

   公网 IP 在 `Data.data[].pppoe_ip_addr`，解析器改为按字段特征识别
   （`ip` / `*_ip_addr` 等），不再依赖固定键名列表。

**顺带发现一个安全问题**：该固件的 `wan` 接口会明文返回 PPPoE 账号与密码
（`username` / `passwd`）。原本"探测原始响应"会把这些直接回吐给浏览器，属于凭据
泄露。现在返回前会递归脱敏（替换为 `***`），公网 IP 等排障必需字段保持可见。

## 五、请求模板（cURL 解析）

管理后台改可信 IP 的请求形态举例（两个版本都支持）：

```
# JSON 体
{"method":"POST","url":"https://work.weixin.qq.com/wework_admin/apps/saveIpConfig?...",
 "body":"{\"app_id\":{app_id},\"trusted_ip_list\":[\"{ip}\"]}"}

# 表单体
app_id={app_id}&ipList%5B%5D={ip}
```

踩过的坑：

1. **cmd 版 cURL 的转义**：`Copy as cURL (cmd)` 会产生 `^&`、`^%^5B`、`^"` 这类转义，
   旧解析器只处理行尾续行，导致 URL/请求头/请求体里残留 `^`，解析结果不可用。
   现在会在分词前统一还原，并把 `Cookie`、`sec-ch-ua*`、`user-agent` 等浏览器特征头
   从模板里剔除（重放时由浏览器会话自己提供）。
2. **两套应用编号**：录制到的请求用的是管理后台内部的 `app_id`（十几位长数字），
   而企业微信 API 用的是 `agentid`（7 位，如 `1230002`）。二者不是一回事，必须分别
   用 `{app_id}` 与 `{agent_id}` 两个占位符；应用记录里同时保存这两个编号。
3. **缺少 `{ip}` 必须报错**：如果模板里没有 IP 占位符，同步会静默写不出最新 IP，
   因此在保存模板时就拒绝，而不是等到同步失败。

## 六、自建应用自动发现

抓取管理后台 `getCorpApplication` 的完整响应后，结构如下：

```
{"data": {"default_app": [102 条腾讯应用], "custom_app": [], "openapi_app": [10 条]}}
```

自建应用与系统应用、腾讯官方应用混在同一个 `openapi_app` 列表里。判别方式只有
`app_open_id` 可靠：

| 类型 | app_open_id | 说明 |
| --- | --- | --- |
| 自建应用 | `1230002` 这类 1 开头的编号 | 它就是 agentid |
| 系统内置（通讯录同步助手、外部联系人） | `2000002` / `2000003` | 必须排除 |
| 腾讯官方应用 | `3010001` | 必须排除 |

两个反直觉的点，都是靠**真实完整响应**才发现的：

1. 自建应用**同样带 `aes_app_id`**，不能拿它当排除条件（早期用截断过的调试样本推断，
   字段正好被截断，结论完全反了）；
2. `app_open_id` 的类型不统一，多数是字符串，个别是**数字**，读取函数必须两种都认，
   否则会漏掉个别应用。

## 七、面板本地管理员账号

加分项：面板自己的登录与微信登录解耦。

- 首次部署进入「创建管理员账号」，单账号；密码用 PBKDF2-HMAC-SHA256（随机盐、20 万次
  迭代）存储，只用标准库；
- 会话令牌带 `sub`（用户名），`require_session` 除了验签还会确认账号仍存在；
- 连续失败 5 次锁定 5 分钟；
- 忘记账号/密码用运维命令 `python -m app.cli list-admins | set-password | reset-admin`，
  Windows 另有 `scripts/admin_cli.ps1` 包装。

### compose 在面板里解析失败

用户把 compose 粘进面板后报：

```
'services[trusted-ip].healthcheck' expected a map or struct, got "string"
'services[trusted-ip].logging'     expected a map or struct, got "string"
```

这是 Go 解析器的错误格式（群晖/宝塔等面板用 Go 解析 YAML）。排查后确认文件本身没问题

处理：`compose.yaml` 去掉 `healthcheck`/`logging` 两个嵌套块（健康检查由镜像自带的
HEALTHCHECK 提供，实测 `docker inspect` 仍为 `healthy`），日志轮转移为注释备选；
并新增没有变量与嵌套块的 `compose.panel.yaml`。

## 十、容器环境下的运维

忘记面板账号时，容器里**仍然使用** `python -m app.cli`，但必须进容器执行：

```bash
docker exec -it <容器名> python -m app.cli list-admins
docker exec -it <容器名> python -m app.cli set-password --username <用户名>
docker exec -it <容器名> python -m app.cli reset-admin
```

镜像里已内置 `PYTHONPATH=/app/backend`，且 CLI 读取的是容器内 `APP_DATA_DIR=/data`
（即 volume 映射出来的同一份数据库）。实测覆盖四种情况：容器内执行、容器停止后用
一次性容器挂同一数据卷执行、群晖 Container Manager 的"终端机"入口、以及宿主机直接
执行（会失败，属预期）。

常见误区：用一次性容器却没挂数据卷 → 命令"成功"但操作的是全新空库。

## 十二、修复同步"假成功"

用户反馈（2026-10-10）：面板显示"已覆盖 N/N 个应用的可信 IP"，但企业微信里
各应用的可信 IP 并没有变。

排查结论 —— 失败被静默吞掉了：

- `backend/app/wecom/admin_browser.py` 的 `replay_request()` 只用
  `response.status >= 400` 判断成败。而企业微信管理后台在会话失效、参数被拒时
  **依然返回 HTTP 200**，真正的原因放在响应体的 `errcode` / `errmsg` 里。
  于是"请求发出去了"就等于"同步成功"，面板与日志都不报错。
- 同文件 `_ensure_logged_in_locked()` 在进程内状态为 `logged_in` 时直接 return，
  不再向企业微信确认。容器长期运行时企业微信侧会话过期，内存里的陈旧状态会继续
  骗过后续请求，所以症状表现为"一开始能用，跑一段时间后就不生效了"。

处理：

1. `backend/app/wecom/parsing.py` 新增 `describe_wecom_error(body)`：解析 JSON 响应，
   `errcode` 非 0 时返回 `errcode=.. msg=..`；成功、非 JSON、无 `errcode` 字段返回 `None`；
2. `replay_request()` 在 HTTP 状态校验之后调用它，被拒绝时抛 `WeComAdminError`，
   企业微信的原始错误码与说明会落到该应用的「最近错误」和同步日志；
3. `ensure_logged_in()` 改为强制访问一次后台核对登录态（`verify_session=True`），
   跳回登录页时把状态置为 `failed` 并提示重新扫码；
4. 补回归测试：`tests/test_wecom_parsing.py` 新增 8 条、新建
   `tests/test_wecom_replay_request.py` 5 条、`tests/test_sync_service.py` 增加
   "被 errcode 拒绝时不得记为成功" 用例 1 条。

本次未解决：企业微信**具体**拒绝原因（会话过期 / app_id 不匹配 / 页面改版）要看真实
返回。修复后「最近错误」会直接显示 `errcode=.. msg=..`，拿到真实错误码再按需处理。

## 十三、手动同步不再被"IP 未变化"挡住

用户反馈（2026-10-10）：企业微信里的可信 IP 已经失效，点面板「立即同步」却提示"已是最新"，
只有勾选"忽略 IP 未变化检查、强制覆盖"才真正写进去。

原因：`SyncService.sync()` 在 `force=False` 时用 `_is_already_synced()` 短路，而它**只读本地
数据库**——"本次观测 IP == 上次观测 IP"且"每个应用 `last_synced_ip` 等于该 IP 且无错误"就整体
跳过，一个请求都不发。`last_synced_ip` 恰好是第十二节那个假成功版本写下的，本地以为已同步、
企业微信里其实没有，于是把"我记得我写过"当成了"企业微信现在就是这个"，企业微信侧被改动后就
再也不会自动修正。

处理：

1. 面板「立即同步」固定按 `force: true` 调 `/api/sync/run`，手动操作一律真正重写全部应用；
   随之删掉已经失去意义的"忽略 IP 未变化检查、强制覆盖"复选框
   （`frontend/src/pages/dashboard.js`）；
2. 自动同步保留"IP 未变化就跳过"的省流行为，跳过文案改为
   "公网 IP 未变化，自动同步已跳过；需要重新写入请在面板点「立即同步」"；
3. 测试：`tests/test_sync_service.py` 新增"上次写入失败的应用不会被 IP 未变化永久跳过、必须
   重试"用例，并在跳过用例中断言文案包含「立即同步」；
4. 同步更新 `README.md` 与 `outputs/deploy/README.md` 中相关说明。

未做（可选项，用户未选）：自动同步在 IP 未变化时每隔 N 小时也强制覆盖一次，作为"企业微信侧
被清过"的安全网。

## 十四、显示真实可信 IP，并按比对结果写入

用户需求（2026-10-10）：应用详情要显示**当前可信 IP**；点「立即同步」时用当前可信 IP 与 iKuai
公网 IP 比对，不一样才覆盖。

背景：此前项目只有"写入"能力（重放 `saveIpConfig`），列表里的可信 IP 实际是本地记录
`last_synced_ip`——第十三节的问题正源于此，把"我记得我写过"当成了"企业微信现在就是这个"。

实现（补上"读取"能力）：

1. **读取模板**：设置新增第二份模板 `wecom_read_template`，面板「企业微信」页多一个
   「读取可信 IP 模板」区块。`frontend/src/pages/wecom.js` 把原模板面板抽成带参数的同一个函数，
   两处复用。校验规则不同：读取模板不要求 `{ip}`，但必须有 `{agent_id}` 或 `{app_id}`
   （`curl_template.validate_read_template`），否则读了也是读到同一份配置。
2. **解析**：`parsing.extract_trusted_ips(body)` 先从 `trusted_ip_list` / `ip_list` / `ipList` /
   `trusted_ip` 等字段名找（忽略大小写与下划线），找不到再退化为"整个数组都是 IPv4"；都识别不出
   返回 `None` 并把原始响应写进 `data/wecom_read_debug.json`（与自动发现调试文件同一套路）。
3. **读取动作**：`WeComAdminSession.read_trusted_ips()` 复用 `replay_request`，因此同样受 HTTP 状态与
   `errcode` 校验保护。
4. **同步编排**：每次同步 → 逐应用读当前可信 IP → 与公网 IP 比对 → **只覆盖不一致的**；读不到时
   回退为直接覆盖（保证最终一致），结果说明里写明"未能读到原值 + 原因"。每个应用结果新增
   `updated` 字段，整次同步状态按"有没有写、有没有失败"汇总：都已是目标值 → `unchanged`，
   写了且全成功 → `ok`，有失败 → `failed`。
5. **存储**：`wecom_apps` 新增 `current_trusted_ips`（JSON）与 `trusted_ip_checked_at` 两列，由
   `_migrate_schema()` 自动补列（老库升级无需手工改库）；`record_app_trusted_ips()` 记录读数并
   清掉上一次的错误。
6. **界面**：仪表盘应用表格新增「当前可信 IP（企业微信）」列（含读取时间），状态徽标改为
   `已最新` / `待更新` / `未知` / `失败`；未配置读取模板时给出提示。企业微信页的应用表同样加列。
7. **测试**：解析（已知字段名 / 字符串值 / 空数组 / 兜底 / 识别不出）、读取模板校验、同步编排
   （一致→不写、不一致→写、多值或空值→写、读失败→回退写、识别不出→回退写）、存储（读数回写、
   清错误、老库升级加列）、API（读取模板解析保存、缺占位符拒绝）。

兼容性：未配置读取模板时行为与改动前一致——`force` 仍决定要不要跳过"公网 IP 未变化"的本地短路。

待办：真实读取请求的响应字段名尚未确认，`extract_trusted_ips` 目前走自适应策略；拿到
`data/wecom_read_debug.json` 后按真实结构收紧，能明显提高读取成功率。

## 十五、识别"返回登录页"的假成功

用户反馈（2026-10-10）：先在**企业微信官网**扫码登录，再回面板检查，面板显示"已登录"、点同步也提示
成功，但企业微信里其实没改。用户判断是官网登录把容器里的会话挤掉了，而系统仍认为已登录。

排查：会话失效时企业微信后台对 ajax 请求往往**返回登录页网页**（HTTP 状态仍是 200，正文里没有
`errcode`），而 `replay_request()` 当时只校验 HTTP 状态码和 `errcode`，网页两者都不命中，于是被当成
写入成功。登录态校验也只看 URL 是否还在 `wework_admin/frame`——会话失效时 URL 可能仍停在 frame
（页面里已经渲染成登录页），因此 `ensure_logged_in()` 也照样通过。这正是第十四节 review 里列为
"可考虑"的那条盲区。

处理：

1. `admin_browser.replay_request()` 增加响应体判断：命中登录页特征（`loginpage_wx` / `login_qrcode` /
   `ww_login_qrcode` / `扫码登录`）时把登录态置为 `failed` 并抛「登录态已失效，请重新扫码登录」；
   其它网页响应抛「返回的是网页而不是接口 JSON，请重新录制请求模板」，不再静默成功；
2. `_ensure_logged_in_locked()` 除 URL 判断外，再用页面里**是否存在登录二维码 iframe** 判断登录页，
   覆盖"URL 仍是 frame 但实际已登出"的情况；
3. 测试：`tests/test_wecom_replay_request.py` 新增"返回登录页"、"返回普通网页"、"URL 未变但页面
   出现二维码"三条回归用例。

说明：企业微信管理后台的会话看起来是**同一账号单会话**，在官网/手机端重新扫码会把容器里的会话挤掉；
识别到之后面板会显示"登录失败/请重新扫码"，同步也会明确失败而不再假成功。

## 十六、写入后回读校验

用户要求（2026-10-10）：既然已经能读取真实可信 IP，就"写入成功后再读回一次确认"，把"报成功但没写进去"
这种情况彻底兜住。

实现（`services/sync_service.py:_sync_one_app`）：

1. 配了读取模板时，写入返回成功后**再读一次**该应用的可信 IP：
   - 读回来就是目标值 → 结果说明标注「（已回读确认）」；
   - 读回来仍是别的值 → 该应用记为**失败**，`last_error` 写「写入已提交，但回读校验不通过：当前可信 IP
     为 X，目标为 Y」，`last_synced_ip` 不更新（保持"没有确认成功"的语义），但 `updated=True`
     表示确实发过写入；
   - 回读本身读不出来（解析不出 / 请求失败）→ 仍按写入结果算成功，但说明里标注「（回读校验未完成）」，
     不假装校验过。
2. 没配读取模板时行为不变：直接按写入结果记录已知状态，说明里不带回读结论。
3. 测试（`tests/test_sync_service.py`）：回读一致 → 成功并带"已回读确认"；回读仍是旧值 → 失败且
   `last_synced_ip` 为空、`last_error` 有说明；回读读不出来 → 成功但带"回读校验未完成"。
   同时把测试里的假会话改成"写入后真的会读到新值"，更贴近真实后台。

代价：每个**需要写入**的应用多一条读取请求（不需要写的不受影响）。单次回读，不加延迟重试；若企业微信
侧存在读缓存导致偶发误报，后续可加一次短延迟重试。

## 十七、定时只读核对与「获取当前可信 IP」按钮

用户反馈（2026-10-10）：当前可信 IP 不该只在点「立即同步」时才读——要么按间隔读，要么给个按钮主动读，
否则没法判断"什么时候需要点同步"。用户选了方案 A（按钮 + 定时只读）。

问题本质：读取原本绑在"同步"上。自动同步关闭时后台不跑同步，面板读数就会一直停在旧值；而用户恰恰是
靠这个读数判断要不要动手。

实现（读取与写入解耦）：

1. `SyncService.refresh_trusted_ips()`：只读核对所有应用的当前可信 IP，复用 `_read_current_trusted_ips`
   的读取与记录逻辑，**不发任何写入请求**；返回 `TrustedIpCheckSummary`（总数 / 失败数 / 说明）。
   未配置读取模板、没有应用清单或登录态失效时抛 `WeComAdminError`。
2. `POST /api/sync/refresh-trusted-ips`：面板按钮走这个接口，返回刷新后的应用清单。
3. 调度器把一轮任务抽成 `SyncScheduler.run_once()`：
   - 自动同步开着且前置条件齐备 → `sync()`（核对 + 只写不一致的）；
   - 否则只要"读取模板 + 应用清单"齐备 → `refresh_trusted_ips()`（**只读**）；
   - 两者都不满足 → 静默跳过。
   这样关掉自动同步后仍有新鲜读数，但绝不会自动改企业微信配置。原先的 `_is_ready()` 拆成
   `_can_sync()` / `_can_refresh()`：读取不需要 iKuai 配置。
4. 前端仪表盘「同步控制」加「获取当前可信 IP」按钮（只读），并在面板下加说明：按钮只读，
   关掉自动同步后仍按间隔读取、但不自动覆盖。
5. 测试：`test_scheduler.py`（新增，4 条：开自动同步→写、关掉→只读、缺 iKuai→只读、缺读取模板→跳过）、
   `test_sync_service.py`（3 条：只读核对不写、缺读取模板报错、读不出的按失败计数）、
   `test_api.py`（2 条：接口返回刷新后的清单、错误转 502）。

取舍：关掉自动同步后仍会每轮产生 N 条只读请求（这是"面板永远可信"的代价）；读数只更新面板，
不写同步日志（它不是同步事件）。

## 十八、按真实响应适配可信 IP 读取

用户反馈（2026-10-10）：点「获取当前可信 IP」时 8 个应用全部报
"响应里没有可识别的可信 IP 列表"，并提供了现场证据：

```json
{"agent_id":"1000010","response_sample":"{\"data\":{\"servicecorp_ip_list\":[],\"invalid_ip_list\":[],\"service_ip_info_list\":[]}}"}
```

结论：

1. 请求本身是通的（HTTP 200、不是登录页、没有 `errcode`），**问题只在解析**：企业微信把企业可信IP
   放在 `data.service_ip_info_list`，而这个字段名不在原有候选里；三个列表又都是空的，兜底策略
   （"整个数组都是 IPv4"）也识别不到空列表，于是判为"读不出来"。
2. 同一响应里的 `servicecorp_ip_list` 是**服务商可信IP**，不能当企业可信IP 用，因此没有把它加进
   候选字段。
3. 列表元素可能不是字符串而是对象（真实字段名带 `info_list` 暗示结构会更复杂），所以解析要能
   从元素对象的 `ip` 字段取值。

处理：

1. `parsing.py`：`_TRUSTED_IP_KEYS` 增加 `service_ip_info_list`（并注释说明与服务商列表的区别）；
   新增 `_values_to_ips()` 支持"元素是对象时取 `ip` / `ipv4` / `ip_address` 字段"；空列表现在返回
   `[]`（表示"当前没有可信 IP"，而不是"读不出来"）；兜底策略同步支持对象数组。
2. `admin_browser.read_trusted_ips()`：**读到空列表时也写 `data/wecom_read_debug.json`**，因为
   "空"最常见的原因就是字段挑错，留档才能看出来。
3. 读取失败的原因落到应用上：`storage.update_app_error()` + `_read_current_trusted_ips()` 的三条
   失败路径都记录原因，面板应用表格的「最近错误」列现在能直接看到"为什么读不到"，不用再翻日志。
4. 新增排查命令 `python -m app.cli check-trusted-ips`（`cli.py`）：逐条打印读取模板、每个应用的
   原始返回与解析结果，只读不改配置。
5. 测试：解析（`service_ip_info_list` 字符串/对象/空列表）、存储（`update_app_error` 保留覆盖记录）、
   同步服务（读取失败原因落到应用）、CLI（缺读取模板时的提示）。

未验证的部分：本次是**按用户提供的真实响应**适配的，`service_ip_info_list` 目前全为空，还没见过
它非空的样子。写入后的回读校验（见十六）正好用来验证：写进去再读回来，如果对得上说明字段选对了；
如果回读一直对不上，说明还要换字段——那时 `check-trusted-ips` 会把原始返回直接打出来。

## 十九、改从应用列表响应读取可信 IP（读取模板不再是必需项）

承接十八节：用户按提示逐条探测，得到决定性结果——`getCorpApplication` **必须用 POST**
（GET 一律 404），而它的 49KB 响应里**就带着目标 IP**；同时确认之前录的那条
`apps/checkIp` 只是"校验 IP 能不能用"的接口，永远读不到当前配置。所以问题不是字段名，
而是**读取接口选错了**。

处理：

1. `parsing.extract_app_trusted_ips(payload)`：从应用列表响应里按 agentid 取出每个应用的可信 IP。
   字段名未知，所以先用"其它应用条目里确实装着 IP 的字段名"当依据（同一个响应里总会有应用配了
   IP），再按该字段名读其余应用；一个字段名都没认出来时返回空字典 = 读不出来，**不会**被误当成
   "没有可信 IP"。
2. `admin_browser`：把"打开应用管理页并捕获后台 XHR"的逻辑抽成 `_capture_app_list_payloads()`，
   `discover_apps()` 与新增的 `read_app_trusted_ips()` 共用（前者解析应用清单，后者解析可信 IP）。
   `_ResponseRecorder.extract_apps()` 换成更通用的 `payloads()`。
3. `sync_service` 改成三段式：**一次读取全部 → 只写不一致的 → 一次回读确认**。
   - 之前是"每个应用读一次、写一次、再读一次"；现在整个同步只多两次页面访问（读 + 校验各一次）；
   - 读取优先用应用列表响应，读不到的应用再退回逐个应用重放「备用读取模板」；
   - 写入后统一回读，按结果给出「已回读确认」/「回读校验未完成」/「回读校验不通过」；
   - `force` 只用于绕过"公网 IP 未变化"的本地短路，读到已经一致的应用不会重复写入。
4. 「读取可信 IP 模板」降级为**可选兜底**（面板改名「备用读取模板（可选）」），
   面板上"未配置读取模板"的提示也去掉了——默认读取不需要任何配置。
5. `python -m app.cli check-trusted-ips` 改成打印每个应用读到的当前可信 IP 与读不到的原因，
   不再依赖读取模板。
6. 测试：解析（按 agentid 归并、从兄弟应用学字段名、排除系统应用、全部为空时返回空字典）、
   同步编排（一致→不写、不一致→写后确认、列表缺失→回退模板、列表读取失败→照写但标注未完成校验、
   回读仍是旧值→报失败）、记录器、CLI。

已知限制：如果**所有应用**都还没配可信 IP，响应里就找不到"装着 IP 的字段名"，
此时读取会判为"读不出来"（仍会照写，只是标注未完成校验）。等至少一个应用配上 IP 后，
字段名就能被识别出来。
